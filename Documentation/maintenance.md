# Maintain one knowledge base

Record reusable findings in the relevant chapter once. Include the game build, source path, version or hash, evidence type, scope and limitations. Link corrections to earlier evidence without rewriting its original certainty. Update [coverage](reference/coverage.md) and [discrepancies](reference/discrepancies.md) when the scope or status changes. A dated manifest or inventory records the input at that time; regenerating it does not silently revalidate older claims.

Keep paths that depend on the machine in ignored `Documentation/local.json`. Add each supported field to the empty example and setup table. Resolve relative values from the configuration directory and treat empty values as unset. Use repository-relative paths for project files and virtual archive paths for native resources. Map optional external research folders through configuration and keep public URLs in the source register. Record dated installation observations in the relevant audit and link them from setup. Check documentation and tools for personal absolute paths and assumed sibling layouts before sharing. Record only minimal native identifiers, signatures and summaries needed to reproduce research. Do not track complete Vanilla files, credentials, saves, temporary output or downloaded mods. Repository and author permissions still apply to code examples.

Check Markdown links, syntax and any affected examples. Verify structural evidence and offline patch assertions independently of game/save/multiplayer tests. Preserve author-reported conditions and call out unavailable tests. If the workspace is read-only, return a proposed edit with its target and evidence. Commits and publication need separate authorization.

Keep user-facing mod changelogs in chronological order, **oldest to newest**. Preserve existing entries in that order and append new versions at the end. Write entries for players: describe controls and gameplay changes; keep implementation details and test results in the internal documentation.
